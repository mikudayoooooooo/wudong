## 2. 后端冲突裁决：operate 二选一

| 维度 | base T3 版（main） | 组员版（分支） | 建议 |
|---|---|---|---|
| 实体 | banner / announcement / finance_record | 同三实体（banner.image varchar(500)，带生效窗口字段） | **组员版**（字段更全） |
| 下发过滤 | status=1 即出 | **生效时间窗 + 置顶 + sort**（service 层过滤） | **组员版**（超集） |
| C 端 URL | `/app/operate/banner/list`、`/app/operate/announcement/list`（分文件推导） | `/app/operate/banner`、`/app/operate/announcement`（合并控制器显式 prefix） | ⚠️ **需裁决**：双方前端各依赖一种 URL |
| finance_record | 表建了，逻辑 Phase 4 | 管理端只读页已做 | **组员版** |
| 管理端 | 仅 CRUD 接口 | CRUD + cool-admin-vue 页面 + 菜单 SQL | **组员版** |
| IGNORE_TOKEN 方式 | 分文件名=资源名推导（§9.3 纪律） | 文件名与模块同名 → 显式 prefix `/app/operate`（其测试通过，合并后需实测匿名豁免生效） | 合并后实测 |

**建议裁决：以组员版为 operate 主版本**（功能超集 + 管理页齐 + 已有测试），保留 base 版的差异点合入。**统一 C 端 URL 到一种**（倾向 `/app/operate/banner/list`、`/app/operate/announcement/list`——语义更清晰且我们前端已按此实现；改组员版路由文件名即可，一处小改）。

**数据库**：两边同表名（banner/announcement/finance_record），synchronize 自动补列；合并后跑一遍种子脚本验证兼容。

## 3. 前端底座：三个方案（需拍板）

两套 `wudong-web/` 都是 Vue3 + Vite + TS + Pinia + vitest，封套约定一致（code===1000 → data），但目录哲学不同：
- 组员版：api 同构（`if (USE_MOCK) return mock; return request(...)` + env 开关）、scss tokens、URL 同步筛选、GET 匿名
- 我们版：api/ 独立目录 + http 层带 **Authorization（裸 JWT）与 POST**、theme.css、完整登录态（LoginModal + token 持久化 + 刷新续期）

### 方案 A：以我们的为底，组员住宿接入（推荐）
- 迁移清单（组员 → 我们）：
  - `api/http.ts` 合并：保留其 query 序列化工具，合入我们的 auth/POST
  - `api/accommodation.ts`、`api/operate.ts` 改造为我们的调用风格（量小）
  - `views/accommodation/`（HotelList 124行 / HotelDetail 366行）、`views/home/HomeView.vue`（208行，与我们首页**功能重叠需二选一或融合**）
  - `components/` 7 个：HotelCard/RoomCard/FilterBar/CalendarTable/BannerCarousel/Ticker/ComingSoonTag
  - `utils/date.ts`、`utils/query.ts`、`mocks/`（calendar 数据工厂可直接用）
  - 路由 +4 行、导航 +2 项
- 预估 **1-2 天**；风险点：scss tokens 与 theme.css 变量合并、FilterBar 的 URL 状态管理
- ⚠️ 首页重叠：他们首页是"banner+公告+精选民宿"，我们首页是七区块（含公告/轮播）→ 融合为一套

### 方案 B：以组员骨架为底，我们移植
- 迁移清单（我们 → 组员）：12 个 view + 10 个组件（FootprintMap/MiniChain/Waterfall/HeroCarousel/PostCard/RouteQuickView/BookingModal/LoginModal/CountUp/SectionHeader）+ session store + 登录链路 + lib/footprint 前端部分；其 http.ts 需扩展 POST + Authorization
- 预估 **2-3 天**；收益：沿用其 README 接入约定与 mock 开关体系；代价：今天完成的对接形态要再适配一遍

### 方案 C：两个站各交各的
- 零迁移，但验收时是"住宿站"和"行社区站"两个割裂产品。不推荐。

> 共同事项（无论 A/B）：统一首页（融合两边）、统一 operate URL（见 §2）、组员 http 的 mock 开关（USE_MOCK env）是否全局沿用
